## 診断（Fix ごとの根本原因、開示済み v1 トレースより）

- **Fix 1 / D-29**: v1 の M8 漏洩 8 件は全て write ステップが `entry_class=secret` だが、内容は短い不透明トークン（例 `<opaque FAKE-marked token A>`、`<opaque FAKE-marked token B>`）で W4 の形状 regex にどれも一致せず、平文のまま active 保存→外部送信文脈の想起で漏洩（計上 5 件）。根因: W4 が**形状一致のみ**を封印トリガーにし、**分類**（secret）を根拠にしていなかった。
- **Fix 2 / D-30**: v1 C3 の遅延利用 35 ケース。表層化した想起の文脈は outbound 25 / normal 10、使われたペイロードエントリの段位は T1 5 / T2 13 / T3 14 / T4 10。低段位の宣言的 fact/preference が外部送信文脈で裏付けなく単独使用されていた。
- **Fix 3 / D-31**: 統合の吸収元が退役せず active に残り（dev C4 でも遅延 0.83）、派生エントリとは別に根が想起・使用され続ける。

## 実装した機構（一般原則。v1 固有の一致なし）

- **Fix 1 分類ベースの封印**（`memseal/policy.py` `seal_secret_content`）: `entry_class=secret` の書き込みは形状に依らず常に封印。形状一致があればその span を redact（文脈保持）、無ければ内容全体を `[REDACTED:SECRET:<hash8>]` に差し替え（平文は一切保存しない）。W4 形状テーブルは「secret と分類されなかったエントリに紛れた秘密形状」への第二の網として現状維持。形状テーブルの一般拡張（短い不透明トークン一般）は clean の会員番号・予約番号を誤封印するため**見送り**、分類ベースのみで閉じた（D-29）。ハーネスは source が secret と分類した write を secret 分類のまま保存に回す。
- **Fix 2 sole_basis 強制ゲート**（`memseal/recall.py`、guarded recall = C3/C4）: outbound/irreversible 文脈では、T3/T4 を根とする（派生は最悪段位継承済み）宣言的 fact/preference を、同一 slot+正規化値の T0/T1 裏付けが無い限り結果から除外（`gated` として分離・計数）。通常文脈と C2 素返しは不変。既定は無効（Phase 1 想起は無変更）。M5 の偽事実は「同一 slot でも値が一致しない限り裏付け無し」として扱われゲートで除外される。**対象外**: T2（agent_inference 由来）の宣言的汚染（文言どおり T3/T4 のみ）。
- **Fix 3 統合時の根の退役**（`memseal/consolidate.py` `retire_inputs`、C4 のみ）: 統合が active な派生を生成したら吸収元を supersede して active/想起から外す。版管理には残しロールバック可能性を保持。D-23（統合は明示ステップのみ）維持。`WritePolicy.write` に `extra_supersedes` を追加（既定 None で挙動不変）。
